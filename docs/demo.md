# Demo environment

Phase 16. Everything here is **SIMULATED**: log records of a fictional company
(`corp.example`) generated by `backend/app/demo/` and sent through the normal pipeline:
ingestion, parsing, enrichment, detection, alerts, correlation. Nothing touches a real
system and nothing offensive runs. Outside addresses come from the documentation ranges
(RFC 5737: 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24); every stored record, event,
alert and incident is flagged `simulated` and labelled SIMULATED in the UI. Why simulated
raw logs: [ADR-0006](decisions/0006-simulated-demo-data.md).

## Load it

With the stack running ([README](../README.md#run-it-locally)) and an admin created:

```bash
docker compose exec backend python -m app.cli demo-load
```

This creates three things, then reports each step and what it triggered:
- the log sources (`demo-linux-auth`, `demo-windows-security`, `demo-network-flows`,
  `demo-web-01-access`);
- the inventory (11 assets, 6 identities), so enrichment and priority use criticality and
  privilege as they would for real logs;
- the story below.

The story is placed relative to an **anchor**: `--start <ISO time>`, by default the start of
the current hour. It ends before the anchor and starts three days earlier, so the dashboard's
recent days are full. The same anchor gives exactly the same records, alerts and incidents.
Loading again with the same anchor stores nothing new: every record is a duplicate, and the
command says so (`1042 records (1042 already stored), 0 new alerts, 0 new incidents`).
Another anchor gives the same alerts and incidents. Only the number of web requests changes
slightly, because the visitors are drawn with a fixed seed per day (1042 records for
`--start 2026-09-25T18:00:00Z`, which CI uses; 1044 for an anchor a week later).
Existing sources and inventory entries are never changed, so an admin's edits survive.

Other commands:
- `cli demo-scenarios`: every scenario and its options.
- `cli demo-ingest --scenario NAME --source SOURCE [--host] [--user] [--source-ip]
  [--count] [--interval] [--start]`: one scenario on its own, with your own parameters (the
  brief's scenario selection, event count, time range, host, user and source IP).
- `cli demo-status`: counts simulated and real records. It exits 3 if any record is real.

Everyone has a fixed workstation and address (`WORKSTATIONS` in `scenarios.py`). Every

## The story

Times are relative to the anchor. The three days of ordinary activity come first, so that
detection has the history a real deployment would have.

| When | Step (scenario) | Records | Must trigger |
|---|---|---|---|
| 3 days | Working days on the web server: key-based SSH, routine sudo, one mistyped password (`benign`) | 30 | nothing |
| 3 days | Working days on Windows: workstation and file-server logons (`normal_authentication`) | 27 | nothing |
| 3 nights | Nightly backups: many connections, two ports (`backup_job`) | 72 | nothing |
| 3 days | Visitors on the web site, health checks every 30 min, scanner 404s (`web_traffic`) | about 760 | nothing |
| −25 h | Password spraying against app-01 from 198.51.100.23 (`password_spray`) | 16 | AUTH-003 |
| −22 h | Brute force against `admin` on jump-01 from 198.51.100.77 (`brute_force`) | 24 | AUTH-001 |
| −19 h | Distributed brute force against `bob` on db-01, six sources (`distributed_brute_force`) | 18 | AUTH-005 |
| −16 h | Success after failures: `carol` on fs-01 from 192.0.2.150 (`brute_force_success`) | 26 | AUTH-001, AUTH-002, AUTH-004 |
| −13 h | Root shell through sudo on build-01, and carol not in sudoers (`privilege_escalation`) | 3 | PRIV-001 (two alerts, one per user) |
| −10 h | New local account added to sudo on mon-01 (`privileged_account_creation`) | 4 | ACCT-001 |
| −7 h | Encoded PowerShell on alice's workstation (`suspicious_process`) | 2 | PROC-001 |
| −4 h | Bob's workstation probing db-01's ports (`network_scan`) | 25 | NET-001 |
| −90 min | Multi-stage attack on web-01 from 203.0.113.45: brute force, logon, root shell, new sudo account (`multi_stage_attack`) | 31 | AUTH-001, AUTH-002, PRIV-001, ACCT-001 |

AUTH-004 (logon from a network new for the account) fires on carol's account only because
the story gives her three days of office logons first. On its own, the scenario triggers
AUTH-001 and AUTH-002 only. The rule needs history to judge, which is what the environment
adds. The other accounts attacked successfully, such as `deploy`, have too little history
for it (fewer than five logons).

**Result: about 1,040 records, 15 alerts, 5 incidents.**

| Incident | Alerts |
|---|---|
| fs-01: carol's account | AUTH-001, AUTH-002, AUTH-004 |
| build-01: root shell | PRIV-001 ×2 |
| mon-01: new privileged account | ACCT-001 |
| ws-042: encoded PowerShell | PROC-001 |
| web-01: the multi-stage attack | AUTH-001, AUTH-002, PRIV-001, ACCT-001 |

The spraying, the bastion brute force, the distributed brute force and the port scan stay
alerts: a lone low or medium alert does not open an incident ([correlation.md](correlation.md)). The attacks
are three hours apart, more than the correlation window (2 h), each on its own host and from
its own address, so each incident is one scenario. `tests/unit/test_demo.py` checks the
spacing. `tests/integration/test_demo_environment.py` checks every row of both tables
against PostgreSQL, and CI checks the totals on the running stack.

## A demonstration

The brief's demonstration chain (§47), on the loaded demo. Sign in as an analyst or admin.

1. **Dashboard**: open alerts and incidents, the SIMULATED note, three days of ingestion.
2. **Alerts**: 15 alerts ordered by priority score, each with its breakdown (severity,
   confidence, asset criticality, privileged identity, evidence volume). Each says which rule fired and why,
   with the evidence events.
3. **Incidents → web-01** ("Multi-stage activity on web-01", the highest risk): one incident
   from four alerts. Each link states its reason, for example "Same host and user (host
   web-01 and user deploy), 33 s apart", or "a new kind of finding" after the access the
   incident shows on web-01. The timeline is rebuilt from the evidence events (the failures,
   the accepted logon, the root shell, the new account), followed by the alerts and the
   engine's activity. The incident lists its ATT&CK techniques (T1110.001, T1078, T1548.003,
   T1136.001 and others).
4. **Investigate**: open an evidence event (raw record and parsed fields); look up web-01
   and `deploy` in Assets and Identities; hunt for other activity from 203.0.113.45 in Hunt.
5. **Act**: add a note, pin evidence, assign the incident, move it to TRIAGED, then resolve
   it with a disposition.
6. **Audit**: Admin → Audit log shows each of those actions, the DEMO_LOADED entry, and (after
   a reset) DEMO_RESET.
7. **Benign look-alikes**: hunt for bob's mistyped password, or the backup server's
   connections to db-01. They are in the data, and no rule fired on them.

## Resetting the demo

```bash
scripts/demo_reset.sh               # asks first; --yes to skip; --start ISO-TIME for the anchor
```

The reset replaces the database with a new one holding the story again
([ADR-0015](decisions/0015-demo-environment-reset.md)). Alerts, incidents, notes, statuses
and the demo's audit log are gone. **User accounts are kept** (passwords and two-factor
too), and everyone signs in again. In order, the script:

1. refuses unless every stored record is SIMULATED (`cli demo-status`), so it never runs
   against a database with real evidence;
2. backs up the database with `scripts/backup.sh` (skip with `--no-backup`), which keeps the
   audit log of the demo just given;
3. notes the audit log's newest entry; it stops here if the audit chain is broken;
4. copies the users table into its own memory (the password hashes are never written to
   disk), recreates the database, lets the backend migrate it, and puts the users back (if
   it fails in between, the accounts are in the backup of step 2);
5. loads the story (`demo-load`). The new audit log's DEMO_RESET entry names the replaced
   log's newest entry. The script then verifies the new chain.

Raw records, events and the audit log are append-only, even for the database's own
application role (ADR-0010). Demo data therefore cannot be deleted row by row, and a reset
must be a new database, as a restore is.

## Limitations

- The data is cleaner than real logs: one format per source, no clock skew, no lost lines.
  The parsers are tested separately against malformed input.
- The company is small (11 hosts, 6 accounts, about 350 records a day), enough to show
  every rule and the correlation, not to show scale. Scale is measured separately with
  generated data in [performance.md](performance.md).
- Attackers use the documentation address ranges, so threat intelligence lookups (not built)
  would find nothing.
- A reset takes the site down while the database is recreated and the story loaded (41 s
  measured on the development machine, including the backup).
